- `RECNUM` is the only column that is unique, non-null and present in every table. It is a surrogate; whether it is stable across ACADE versions/re-exports is **not known (assumption: it is not)**. Use it as the technical PK of the SQL copy, and for repeatable upsert from the same file.

Recommendation (conclusions drawn from the counts above):
- `RECNUM` is the only column that is unique, non-null and present in every table. It is a surrogate; whether it is stable across ACADE versions/re-exports is **not known (assumption: it is not)**. Use it as the technical PK of the SQL copy, and for repeatable upsert from the same file.
- For sync across different versions of the catalog, no single natural key works for the family tables: (MANUFACTURER, CATALOG) is unique in only some tables; (MANUFACTURER, CATALOG, ASSEMBLYCODE) in others; many tables have duplicate keys or NULL ASSEMBLYCODE. See the lists above for exactly which. Where 'whole-row distinct' is the only guarantee, upsert can use a hash of all non-RECNUM columns (NULL-safe).
- Keys containing ASSEMBLYCODE are mostly NULL in that column (e.g. MS 254,998 of 269,772). A UNIQUE constraint over a nullable column behaves differently per engine (SQLite/PG: many NULLs allowed, i.e. NOT unique; MSSQL unique index: only one NULL). Do not declare such composites as UNIQUE in the target; use RECNUM as PK and treat natural keys as non-unique lookup indexes, or compute a NULL-safe row hash.
- `_PINLIST_*`: (MANUFACTURER, CATALOG, ASSEMBLYCODE) is not unique everywhere; see list. `_TERMPROPS_*`: LEVELS participates in the key where it is unique.
- footprint_lookup: (CATALOG, ASSEMBLYCODE, BLKNAME|BLKNAM) is the best natural candidate but is not unique everywhere and ASSEMBLYCODE is often NULL and sometimes space-padded; duplicates exist in GUILD (case/trim-only), SCE, SIEMENS, SQD, TELEMECANIQUE (rows identical, or identical after upper+trim, apart from RECNUM). In `SCE` the same CATALOG maps to different ASSEMBLYCODE values and vice versa (see samples.txt).

## 4. Read throughput (largest catalog table `MS`, 269,772 rows, 19 columns incl. 2 MEMO)

Observed during profiling run (batches in the same connection, one after the other):

- fetchmany(1000) : 269,772 rows in 3.38 s = 79,700 rows/s
- fetchmany(5000) : 269,772 rows in 18.15 s = 14,860 rows/s
- fetchmany(20000) : 269,772 rows in 17.96 s = 15,024 rows/s
- fetchall : 269,772 rows in 18.25 s = 14,779 rows/s

Re-run with a fresh connection per scan (`04_throughput.py`):

- batch 20000: 269,772 rows in 4.29 s = 62,905 rows/s
- batch 1000: 269,772 rows in 16.18 s = 16,677 rows/s
- batch 5000: 269,772 rows in 18.18 s = 14,839 rows/s
- batch 1000: 269,772 rows in 17.58 s = 15,349 rows/s
- batch 20000: 269,772 rows in 17.92 s = 15,058 rows/s
- batch all: 269,772 rows in 18.32 s = 14,726 rows/s

Finding: the very first scan in a process runs at ~60-80k rows/s (4-5 s for MS); every later scan of the same table, even on a new connection, runs at a steady ~15k rows/s (~18 s), independent of batch size (1,000 to 20,000, fetchall). Cause not determined (assumption: ACE engine cache/memory behaviour inside the process). Plan with the conservative figure: ~15k rows/s means the whole catalog (1,594,493 rows) reads in roughly 110 s and footprint_lookup (261,858 rows) in ~17 s (measured 17 s including profiling). Batch size is not a lever; 5,000-10,000 is fine for memory. The SQL insert side will likely be the bottleneck, not the read.
